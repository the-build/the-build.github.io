# Datadog 벤치마킹 — 자체 모니터링 플랫폼에 무엇을 가져올까

오케스트로에서 OpenStack 과 Kubernetes 자원을 한 화면에서 보는 통합 모니터링 플랫폼을 개발했습니다. 고객이 금융·공공기관이라 SaaS 를 쓸 수 없고, 수집부터 저장·시각화까지 직접 만들어야 했습니다.

직접 만들다 보면 "이 정도면 잘 만든 건가?" 를 판단할 기준점이 필요합니다. 그래서 상용 모니터링의 대표 격인 **Datadog** 을 기준점으로 삼았습니다. Datadog 공식 유튜브 채널의 영상을 보며 스터디하고, 공식 문서로 확인하면서 정리한 내용입니다.

---

## 1. 우리 플랫폼은 이렇게 생겼다

먼저 비교 대상인 우리 쪽 구조입니다.

- **수집**: OpenStack·Kubernetes 자원 지표를 주기적으로 수집
- **변화 감지**: Redis 에 직전 상태를 두고 비교해, 바뀐 자원만 Kafka 로 흘려보냄
- **저장**: 로그·자원 데이터는 OpenSearch, 시계열 메트릭은 Thanos
- **서비스**: Spring Cloud Gateway/Config, WebFlux 기반 마이크로서비스
- **실시간 화면**: RSocket 으로 대시보드에 스트리밍
- **연동**: DB·WAS 등 다른 회사의 모니터링 솔루션 데이터를 받아 한 화면에 시각화

---

## 2. Datadog 은 어떻게 생겼나

### (1) Agent 하나 + 연동(Integration)

- 호스트마다 **Agent 하나**를 설치하면 시스템 지표·로그·트레이스를 같이 보냅니다.
- DB, 웹 서버, 메시지 큐, 클라우드 같은 대상은 **수백 개의 연동 설정**으로 붙입니다. 연동을 켜면 그 대상용 기본 대시보드가 같이 생깁니다.

### (2) 모든 데이터는 태그로 묶인다

- 메트릭·로그·트레이스 모두 `key:value` 태그를 답니다.
- 특히 **`env`, `service`, `version` 세 가지 태그를 모든 데이터에 똑같이 다는 것**(Unified Service Tagging)을 권장합니다. 이 세 태그가 같으면 메트릭에서 로그로, 로그에서 트레이스로 한 번에 넘어갈 수 있습니다.

### (3) 태그 조합 = 비용

- Datadog 은 커스텀 메트릭을 **메트릭 이름 + 태그 값 조합** 하나하나로 셉니다.
- `user_id` 처럼 값이 끝없이 늘어나는 태그를 달면 조합이 폭발합니다. 비용 문제이기 전에 **저장소가 감당할 수 있는 카디널리티(cardinality)** 의 문제입니다.

### (4) 로그는 "받기" 와 "색인하기" 를 나눈다

- 로그는 일단 전부 받되, **검색용으로 색인할 것만 골라** 저장합니다. 나머지는 지표로 뽑아 두거나 아카이브로 보냅니다.
- "다 저장하고 다 검색" 하지 않는다는 점이 핵심입니다.

### (5) 대시보드보다 알림

- Monitor 는 고정 임계값 말고도 **이상 탐지(anomaly)·예측(forecast)·이상치(outlier)** 방식을 고를 수 있습니다.
- Watchdog 은 사람이 규칙을 걸지 않아도 평소와 다른 패턴을 먼저 알려 줍니다.

## 3. 나란히 놓고 보기

| 항목 | Datadog | 우리 플랫폼 | 비춰 보고 정리한 것 |
|---|---|---|---|
| 수집 | Agent 하나 + 연동 설정 | 대상별 수집기 → Kafka | 연동 단위로 "수집 + 기본 화면" 을 묶으면 수집 대상을 늘리기 쉽다 |
| 데이터 모델 | 태그 중심, `env`/`service`/`version` 통일 | 자원 종류별 데이터 | 공통 라벨이 있어야 메트릭·로그·이벤트 화면을 오갈 수 있다 |
| 메트릭 저장 | 시계열 전용 저장 | OpenSearch → **Thanos 로 이관** | 시계열은 시계열 저장소로. 고가용성과 장기 보존을 위해 Thanos 로 옮겼다 |
| 로그 | 받기와 색인 분리 | OpenSearch 에 저장·검색 | 검색할 로그와 보관만 할 로그를 나누는 기준이 필요하다 |
| 중복 조회 | 서버 쪽 집계·롤업 | 주기 수집 + 캐싱 | 같은 쿼리를 여러 화면이 반복하지 않도록 미리 모아 두고, 월별 인사이트 데이터로 재사용했다 |
| 이기종 연동 | 연동 카탈로그 | DB·WAS 솔루션 연동 | 외부 솔루션도 같은 라벨 체계로 받아야 한 화면에서 의미가 생긴다 |

---

## 4. 배운 것

1. **태그(라벨) 설계가 먼저다.** 화면을 만들기 전에 모든 데이터에 공통으로 달 라벨을 정해야 메트릭·로그·이벤트를 오갈 수 있습니다.
2. **카디널리티는 설계 단계에서 막는다.** 값이 무한히 늘어나는 라벨은 메트릭이 아니라 로그로 보냅니다.
3. **수집과 색인은 다른 결정이다.** 다 받되, 다 검색할 필요는 없습니다.
4. **시계열은 시계열 저장소에.** 범용 검색 엔진에 메트릭을 쌓으면 결국 보존 기간과 비용에서 막힙니다.
5. **대시보드보다 알림 기준.** 사람이 화면을 계속 볼 수는 없으니, "언제 사람을 부를지" 가 모니터링의 끝입니다.

---

## 5. 정리

Datadog 을 그대로 따라 만들 수는 없습니다. 온프레미스·폐쇄망 고객이라는 조건이 다르고, Datadog 의 많은 기능은 거대한 SaaS 백엔드 위에 있습니다. 하지만 **"태그로 묶고, 수집과 색인을 나누고, 시계열은 시계열답게, 알림으로 끝낸다"** 는 원칙은 규모와 상관없이 가져올 수 있었습니다.

자체 모니터링을 만들고 있다면, 기능 목록보다 이 원칙들을 기준점으로 삼아 보길 권합니다.
